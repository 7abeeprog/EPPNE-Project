# نسبة `birth_date IS NULL` في جدول `users` — فحص مباشر على DB (read-only)

**تاريخ:** 2026-09-16
**النطاق:** استعلام SQL مباشر بس (`SELECT` بحت)، صفر تعديل كود، تكملة لـ
[[project_guardian_relationship_design_planning]] — الهدف تحديد جاهزية
`birth_date` كمصدر بيانات لتصميم migration علاقة ولي أمر↔طالب النهائي.
**ممنوع أي تعديل كود — تم الالتزام، صفر Edit/Write على كود المشروع.**

---

## الاستعلام والنتيجة

**البيئة:** container `eppne_db` (Postgres 16)، قاعدة البيانات `eppne_v2`
(تم التأكد بـ `psql -l` إن دي القاعدة الفعلية — الحاوية التانية
`postgres-eppne` غير مستخدَمة هنا، نفس منهجية الجلسات السابقة).

```sql
SELECT COUNT(*) FILTER (WHERE birth_date IS NULL) * 100.0 / COUNT(*) AS null_percentage,
       COUNT(*) as total_users
FROM users;
```

```
   null_percentage   | total_users
---------------------+-------------
 99.1596638655462185 |         119
```

**تفصيل إضافي (استعلام تكميلي للتأكيد):**

```sql
SELECT COUNT(*) FILTER (WHERE birth_date IS NULL) AS null_count,
       COUNT(*) FILTER (WHERE birth_date IS NOT NULL) AS not_null_count,
       COUNT(*) AS total_users
FROM users;
```

```
 null_count | not_null_count | total_users
------------+----------------+-------------
        118 |              1 |         119
```

**النتيجة: 99.16% من إجمالي 119 مستخدم (118 من 119) عندهم `birth_date =
NULL`. مستخدم واحد فقط (0.84%) عنده قيمة مسجَّلة فعليًا.**

---

## الملاحظة المطلوبة: أثر هذه النسبة على قرار "غير معروف = يحتاج تحقق إداري"

هذه مجرد ملاحظة توضيحية — **بلا أي تغيير على القرار نفسه**، ولا أي
توصية بتعديله في هذه الجلسة.

النسبة (99.16%) **أعلى بكثير جدًا** من عتبة الـ50% المذكورة في السؤال —
عمليًا **كل قاعدة المستخدمين الحالية تقريبًا (باستثناء مستخدم واحد) بلا
`birth_date` مسجَّل**. لو تصميم علاقة ولي أمر↔طالب النهائي يتبنى قاعدة
"`birth_date` غير معروف → يُعامَل كحالة تحتاج تحقق إداري صريح (مش يُفترض
تلقائيًا راشد ولا قاصر)"، فالأثر العملي المباشر:

- **أي طالب حالي تقريبًا** (118 من 119 مستخدم، عبر كل الأدوار — مش بس
  الطلاب تحديدًا؛ هذا الاستعلام على جدول `users` بالكامل بلا فلترة حسب
  الدور، لأن لا يوجد عمود دور طالب/غير طالب صريح يمكن الفلترة عليه بثقة
  في هذا السياق) **سيدخل تلقائيًا في طابور "يحتاج تحقق إداري"** فور
  تفعيل علاقة ولي أمر↔طالب — مش استثناء نادر، بل هو **الوضع الافتراضي
  الفعلي** لكل قاعدة المستخدمين الحالية.
- هذا **يحمّل الأدمن حجم مراجعات ضخم فورًا عند الإطلاق** (أقرب لعملية
  "مراجعة كل مستخدم قائم" أكثر من كونه استثناءً هامشيًا لعدد قليل من
  الحالات الغامضة) — خصوصًا في ظل النتيجة الموثَّقة سابقًا في
  [[project_guardian_relationship_design_planning]]: **لا توجد أي بنية
  تنبيه فعلية للأدمن اليوم** (لا `send_notification` ولا `event_bus`
  مربوطين بأي طابور تحقق قائم، ولا حتى استعلام لجلب "كل الأدمنز").
  اجتماع الأمرين (حجم مراجعات ضخم + صفر بنية تنبيه) يعني إن الأدمن لن
  يعرف حتى بوجود هذا الحجم إلا بفحص القائمة يدويًا بشكل دوري.
- بديل تصميمي محتمل (**قرار منتجي خارج نطاق هذه الجلسة القرائية بالكامل**،
  مذكور هنا كملاحظة سياقية فقط): معاملة `birth_date IS NULL` كـ"راشد
  افتراضيًا حتى إثبات العكس" بدل "يحتاج تحقق إداري"، أو طلب إدخال
  `birth_date` كخطوة إجبارية أولى في تدفق طلب ربط ولي الأمر نفسه (بدل
  الاعتماد على القيمة المخزَّنة مسبقًا في `users`) — بيقلل الحمل على
  الأدمن لأنه يحوّل "تحقق جماعي فوري" إلى "تحقق فردي وقت الحاجة الفعلية
  فقط".

**لا يوجد أي تغيير على القرار المعماري نفسه في هذه الجلسة — فقط توثيق
الحجم الفعلي المترتب عليه، عشان يكون معروفًا وقت تصميم الـmigration
النهائي.**
