# جلسة `user-repository-get-user-audit` — Backlog #8

## السياق (خلفية كاملة، لا حاجة للرجوع لأي محادثة سابقة)
مشروع **EPPNE** (Backend FastAPI). جلسة `user-repository-get-by-id-audit`
(Backlog #1، مغلقة، آخر commit) أغلقت فئة "معامل `tenant_id` ناقص" لـ15
موضع. **هذا بند مختلف تمامًا رغم تشابه الاسم**: `UserRepository` **ليس
عندها method اسمها `get_user()` إطلاقًا** — أي استدعاء لـ`.get_user(`
عليها هو `AttributeError` مباشر، مش `TypeError` بمعامل ناقص. لا تخلط
بين البندين.

**الوصف التاريخي الموثَّق (تحقق بنفسك، لا تفترض دقته — نفس الوضع اللي
كان مع #1، حيث القايمة القديمة كانت صحيحة 100% لكن التحقق الجديد كشف
موضع ناقص من التوثيق نفسه):** آخر جرد `grep` موثَّق رجّع **6 مواضع**:
`communications/service.py:29`, `communications/service.py:36`,
`digital_twin/service.py:51`, `employment/service.py:89`,
`health/service.py:54`، وموضع سادس غير مسمى صراحة في آخر ملخص متاح —
**تأكد من العدد الحقيقي بنفسك، لا تفترض 6 هو الرقم النهائي.** موضع
تانٍ (`identity/service.py:238`) اتفحص سابقًا وتأكَّد إنه **صحيح مش
باج** (بينادي method حقيقية على `UserService` نفسها، مش على
`UserRepository`) — تحقق بنفسك من هذا الاستثناء بدل افتراضه.

**سبب الأولوية الآن:** جلسة `user-repository-get-by-id-audit` (Backlog
#1) أثبتت حيًا أن سلسلة `affiliate`/Backlog #10 وصلت لـ10 دومينات
لطبقة `User.referred_by` المفقود، **لكن `digital_twin` و`employment`
لسه محجوزين عند طبقة أسبق تمامًا (Backlog #8 هذا بالذات)** — لم
يصلوا حتى لـ`get_by_id` بعد. حل #8 هو الخطوة اللازمة لدفع هذين
الدومينين للطبقة نفسها اللي وصلها الـ10 الباقيين.

## القاعدة الصارمة (نفس منهجية كل الجلسات السابقة، بلا استثناء)
- **صفر تنفيذ فوري.** ابدأ بـ`grep` شامل جديد بالكامل من الصفر لكل
  استدعاء فعلي لـ`.get_user(` على أي كائن من نوع `UserRepository`
  (ميّز بدقة عن `.get_user(` على كائنات تانية زي `UserService` — نفس
  التمييز اللي حصل مع `identity/service.py:238` سابقًا) عبر المشروع
  كله. لكل موضع:
  1. هل المشكلة لسه موجودة فعليًا اليوم؟ (جلسات كتير حصلت من وقت آخر
     توثيق لهذا البند — savepoint fixes، redis wrapper، affiliate، #1)
  2. هل الاستدعاء محمي بـ`try/except` صامت، أم بيكسر الطلب بوضوح؟
  3. أقرب method حقيقية موجودة على `UserRepository` تقدر تحل محل
     `get_user()` هي `get_by_id(user_id, tenant_id)` — تأكد من مصدر
     `tenant_id` المتاح في نطاق كل دالة (نفس منهجية #1 بالضبط: معامل
     مباشر، معامل في دالة أم مش ممرَّر، مُشتق من صف محمَّل، أو غير متاح
     إطلاقًا).
  4. حدّث القايمة القديمة بالكامل — مواضع اتصلحت، مواضع جديدة، تصحيحات.
- **اعرض القايمة الكاملة المحدَّثة للموافقة قبل أي سطر كود.**
- **انتبه بخصوص `digital_twin` و`employment` تحديدًا**: هذان الدومينان
  مرتبطان مباشرة بسلسلة `affiliate`/Backlog #10 المفتوحة. بعد إصلاح
  هذا البند، تحقق (توثيق فقط، بلا إصلاح) هل وصلا الآن لنفس طبقة
  `User.referred_by` المفقود اللي وصلها الـ10 دومينات الأخرى — نفس
  النمط بالضبط المتبع في جلسة #1 (تحقق ختامي بلا إصلاح للطبقة التالية).
- **أسلوب الإصلاح**: بناءً على نمط جلسة #1 (لا يوجد base class مشترك
  بين خدمات الدومينات)، الأرجح إصلاح per-site (كل موضع يستبدل
  `.get_user(user_id)` بـ`.get_by_id(user_id, tenant_id)` مباشرة) —
  لكن تحقق بنفسك ولا تفترض؛ اعرض التصميم المقترَح للموافقة قبل التنفيذ،
  زي كل مرة.
- **تحقق حي إلزامي لكل موضع** — صفر ثقة في "compiles clean". بيانات
  throwaway أو بيانات موجودة (نفس أسلوب #1 اللي استخدم مستخدم حقيقي
  موجود مسبقًا لتفادي بيانات throwaway إضافية، لو مناسب هنا) مع تنظيف
  كامل لو احتجت بيانات جديدة.
- **regression test دائم إجباري**: `tests/test_user_repository_get_user_audit.py`
  + README مخصص، قبل أي commit.
- **أي اكتشاف جانبي جديد**: توثيق فوري بدليل كود صريح، صفر إصلاح تلقائي،
  توقف واعرض على المستخدم — نفس القاعدة الثابتة دايمًا.
- **Commit معزول واحد** في النهاية. اعرض `git status` نهائي للموافقة
  قبل الـcommit الفعلي.
