# جلسة `redis-client-wrapper-missing-methods` — المرحلة 1.4 (Backlog #7)

## السياق (خلفية كاملة، لا حاجة للرجوع لأي محادثة سابقة)
مشروع **EPPNE** (Backend FastAPI). جلسة `regression-tests-backfill`
السابقة (مغلقة، commit `0c1db51`) أكَّدت بالقراءة المباشرة أن
`RedisClientWrapper` (`app/core/redis_client.py`, حوالي السطر 24-141)
فيها الميثودز الأساسية (`get`, `set`, `delete`, `incr`, `expire`, `ping`,
`publish`, `get_json`, `set_json`, إلخ) لكنها **ناقصة تحديدًا**:
`hincrbyfloat`, `pubsub`, `lpush`, `ltrim`, `hgetall`.

## لماذا أولوية عاجلة (مُرقّاة من المرحلة 3 الأصلية لـ1.4)
مؤكَّد حيًا في جلسات سابقة (`ai-agents-execute-action-fix`) أن غياب
`hincrbyfloat` تحديدًا **يُسقط `execute_agent_action` بالكامل** —
مش بس فشل تتبع تكلفة. الاستخدامات المعروفة:
- `services/ai/cost_tracker.py` — `hincrbyfloat` لتتبع تكلفة AI تراكميًا.
- `services/ai/cache.py` — على الأرجح `hgetall`/`get_json` مرتبطة.
- `communications/router.py` — `pubsub`/`lpush`/`ltrim` (احتمال قنوات
  إشعارات أو طوابير رسائل — تأكَّد بالقراءة المباشرة، لا تفترض).

**قبل أي سطر كود، اقرأ الثلاثة ملفات دي فعليًا** (`cost_tracker.py`,
`cache.py`, `communications/router.py`) لتحديد التوقيع المطلوب بالظبط
لكل method (المعاملات، نوع الإرجاع) بناءً على طريقة الاستخدام الفعلية
في الكود المستدعي — مش من توثيق Redis العام فقط.

## القاعدة الصارمة (منهجية كل الجلسات السابقة)
- **نقطة تعديل واحدة، أثر واسع**: التعديل في `RedisClientWrapper` نفسها
  فقط (نفس نمط إصلاح `EventBus.publish()` في جلسة سابقة — ميثود واحدة/
  عدة ميثودز في مكان واحد، تصلح دومينات كتير دفعة واحدة).
- **صفر تنفيذ فوري** — ابدأ بمرحلة تشخيص: اقرأ الكود الحالي لـ
  `RedisClientWrapper` كاملاً، ثم اقرأ كل استخدام فعلي حالي (`grep`) لكل
  method من الخمسة عبر المشروع كله، ووثّق قايمة كل موضع هيتأثر (نفس
  أسلوب `EventBus.publish()` — قسم "يصلح X دومين بتعديل نقطة واحدة").
  اعرض القايمة دي للموافقة **قبل** كتابة أي كود.
- **تحقق حي إلزامي** — نفس معيار كل الجلسات: صفر ثقة في "الكود بيتكمبايل".
  لكل method مُضافة، تحقق حي فعلي ضد Redis حقيقي (نفس الـcontainer
  المستخدم في الجلسات السابقة)، مش mock:
  - `hincrbyfloat`: قيمة تراكمية فعلية تتأكد بـ`HGET` مستقل بعدها.
  - `pubsub`: subscriber مستقل يستلم رسالة فعلية (نفس نمط اختبار
    `eventbus-publish-fix` السابق).
  - `lpush`/`ltrim`: قايمة فعلية في Redis، تتأكد بـ`LRANGE` مستقل.
  - `hgetall`: hash فعلي، تتأكد بمطابقة كل الحقول.
- **regression test دائم إجباري** — من قرار سياسة Regression Tests
  المعتمد [2026-08-18]: لا تُعتبر هذه الجلسة مُغلَقة رسميًا بدون كتابة
  `tests/test_redis_client_wrapper_missing_methods.py` (+ README مخصص
  جنبه، بنفس نمط جلسة `regression-tests-backfill` — مرجع أصلي، ماذا
  يتحقق، أي استثناء). هذا **ليس منقولاً من سكريبت قديم** (لأن هذه أول
  جلسة تعالج #7 فعليًا) — يُكتب من الصفر بناءً على التحقق الحي في هذه
  الجلسة نفسها.
- **بعد إصلاح `RedisClientWrapper`**: تحقق إن `execute_agent_action`
  (الموضع المتأثر الأخطر) بيشتغل فعليًا الآن — استدعاء حي كامل، ليس
  مجرد تشغيل test منعزل على الميثود نفسها. لو ده يكشف احتياج للـ2
  الموضعين المستثنيين سابقًا (`realestate:232`, `invitations:415`،
  الموثَّقين في `ai-agents-execute-action-commit-inside-begin-nested`)،
  **لا تلمسهم** — هذا خارج نطاق #7 صراحة، برغم أي تحسّن ظاهري.
- **أي اكتشاف جانبي جديد** (باج غير متعلق بـ#7 يظهر أثناء القراءة أو
  الاختبار) — نفس القاعدة الثابتة: توثيق فوري في `PROGRESS_LOG.md` كبند
  Backlog منفصل بدليل كود صريح (سطر + سبب دقيق)، صفر إصلاح تلقائي، توقف
  واعرض على المستخدم قبل أي قرار.
- **بيانات throwaway منفصلة لكل تحقق حي**، تنظيف كامل بعد التأكيد
  (مفاتيح Redis بادئة واضحة زي `REGTEST:` عشان يسهل التأكد من عدم بقاء
  مفاتيح يتيمة).
- **Commit معزول واحد** في نهاية الجلسة: التعديل في
  `app/core/redis_client.py` + ملف الـtest الجديد + README + تحديث
  `PROGRESS_LOG.md`. صفر تلوّث من أي تعديل غير مرتبط.
