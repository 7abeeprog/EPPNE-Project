# Phase 8 — الخطة الرئيسية (Master Roadmap) لمشروع EPPNE

> هذا ملف مرجعي استراتيجي دائم، مش ملف تنفيذ. كل مرحلة فيه هتاخد
> phase file منفصل خاص بيها وقت التنفيذ الفعلي.
> راجع SKILL.md وPROGRESS_LOG.md قبل أي عمل — هذا الملف يكمّلهم، مش يحل محلهم.

## السياق
- كل الـ 34 دومين backend **مبنية بالفعل وموسّعة** (حسب تأكيد المستخدم)،
  بما فيهم منطق التمويل الجماعي (موزّع بين `projects` و`finance`).
- المرحلة الحالية للمشروع: **مراجعة + توثيق + نشر**، مش بناء ميزات
  جديدة من الصفر (إلا لو المراجعة كشفت نقص فعلي في دومين معين).
- Phase 0-7 (موثّقة في PROGRESS_LOG.md) عالجت: دمج auth→identity بالكامل،
  ثغرة PUT /api/ai/routing، تأكيد schema عزل tenant_id في iot/privacy.

## ⚠️ مشكلة تشغيلية يجب حلها قبل البدء
جلسات Phase 6 و7 واجهت مشاكل متكررة في shell integration (أوامر بسيطة
زي `cd` بتاخد دقايق أو بتفشل بـ timeout). لازم تتحل الأول (مراجعة
Terminal > Integrated > Shell Integration في VS Code settings) قبل
البدء في مراجعة 34 دومين — وإلا هيضيع وقت ضخم غير ضروري.

## القطاعات وترتيب الأولوية

### المجموعة 1 — قطاعات اعتمادية (Infrastructure/Shared) — 6 دومينز
لازم تشتغل صح مهما كان القطاع الرئيسي المستخدَم:
`identity` (كان auth، دُمج)، `affiliate`, `invitations` (فيه .bak متروك),
`invoicing` (بلا __init__.py + بلا frontend)، `saas`, `sovereign_entities`
(فيه تكرار مع entities/ في الفرونت).

### المجموعة 2 — قطاعات رئيسية (MVP) — 3 دومينز
`commerce` (لاحظ تعارض تسموي مع صفحة `store` في الفرونت)، `academy`
(أكبر دومين، 23 جدول، يحتضن AcademyTenant)، والتمويل الجماعي
(`projects` + `finance` — **يحتاج تأكيد أول خطوة: هل منطق الـ campaigns/
pledges موجود فعليًا ولا بس بنية wallet عامة**).

### المجموعة 3 — باقي القطاعات (25 دومين)
كل الباقي من قائمة الـ 34، بترتيب أولوية يُحدَّد لاحقًا بناءً على الطلب
الفعلي بعد إطلاق MVP، وليس كله دفعة واحدة.

## المراحل الكبرى (بالترتيب)

### المرحلة أ — مراجعة أمنية + جرد وظيفي (المجموعة 1 + 2 أولاً، 9 دومينز)
لكل دومين، الجلسة المخصصة له لازم تنتج 3 مخرجات:
1. **تقرير أمني**: authz فعلي على كل endpoint (مين يقدر يعمل إيه فعليًا،
   مش بس هل فيه Depends)، عزل tenant_id فعلي وقت الاستعلام (مش بس وجود
   العمود في الجدول — نفس الفحص اللي عملناه في repository.py لسه معلّق
   من Phase 7)، input validation، أي ثغرات مكشوفة.
2. **جرد وظيفي (Functional Inventory)**: كل endpoint + الغرض منه +
   المدخلات/المخرجات + حالته الفعلية (شغال / مكسور / كود ميت). هذا
   الجرد هو الأساس اللي هتُبنى عليه خريطة user journey لاحقًا — لازم
   يكون دقيق ومبني على فحص فعلي، مش افتراض من اسم الملف.
3. **تناغم Backend/Frontend**: هل كل endpoint له استهلاك فرونت إند
   فعلي؟ فيه endpoints يتيمة (بدون واجهة) أو العكس (واجهة بتستهلك
   endpoint مش موجود/معطوب)؟

**ترتيب التنفيذ داخل هذه المرحلة:** المجموعة 1 (6 اعتمادية) أولاً —
لأن المجموعة 2 بتعتمد عليها تقنيًا (لا معنى لمراجعة commerce قبل
التأكد من identity وinvoicing). بعدها المجموعة 2 (3 رئيسية).

**كل دومين = phase file منفصل** (مثال: phase9-audit-identity.md،
phase10-audit-invitations.md، ...) — نفس النمط اللي اتبعناه من البداية.

### المرحلة ب — نشر MVP على سيرفرات مجانية
بعد ما المجموعة 1+2 (9 دومينز) تخلص مراجعة وتناغم. بنية قابلة للتوسع
لاحقًا (stateless services، لا تخزين محلي)، مش بنية ضخمة من الأول.

### المرحلة ج — تفعيل وكلاء الذكاء الاصطناعي (بترتيب المخاطرة، الأقل أولاً)
1. وكيل خدمة عملاء/مبيعات (الأقل خطورة، استشاري بالأساس)
2. التوأم الرقمي (Digital Twin — الدومين موجود backend، يحتاج تأكيد
   هل فيه AI agent فعلي عليه أو data model بس)
3. وكيل المستأجرين (tenants)
4. وكيل إدارة التطبيق (الأعلى خطورة — **صلاحياته لسه غير محددة**:
   تنفيذي/يقدر يعدّل بيانات، ولا استشاري بس؟ هذا قرار لازم يُحسم قبل
   البناء، ومرتبط مباشرة بموضوع نظام الصلاحيات (لا يوجد RBAC حاليًا،
   فقط get_current_user/get_current_superuser الثنائي))

**اختيار النموذج اللغوي**: معلّق لحد ما يتحدد: الميزانية، مستوى حساسية
البيانات لكل وكيل، هل محتاج tool-use قوي (للوكيل التنفيذي) أو رد نصي
بس (لخدمة العملاء)، والأداء بالعربي.

### المرحلة د — تحسين UX/Design (يمكن أن تبدأ بالتوازي مع ب/ج)
تحسين تجربة العميل، أكثر من طريقة دفع (سيمث وغيرها).

### المرحلة هـ — التوسع لباقي القطاعات (25 دومين المجموعة 3)
قطاع قطاع، بترتيب أولوية يُحدَّد بعد إطلاق MVP وفيدباك حقيقي من
مستخدمين، وليس كله دفعة واحدة.

### المرحلة و — تطبيق الموبايل
بعد استقرار الـ API بالكامل (تغيير الـ API بعد بناء موبايل عليه
يضاعف الشغل).
